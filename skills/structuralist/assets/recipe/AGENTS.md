# {{PROJECT_NAME}} Repository Instructions

This repository keeps an explicit project-owned unformalized Region with
Mindflow.

## Read Before Changing

1. Read [governance/Documentation.md](governance/Documentation.md).
2. Read [profiles/README.md](profiles/README.md) and the profiles that own the
   subject.
3. For implementation work, read
   [canonical_docs/README.md](canonical_docs/README.md) and the affected
   contract.
4. Read [long_term_steering/README.md](long_term_steering/README.md) for current
   developing direction.
5. Map the complete present document structure before adding durable prose,
   then read affected owners and dependencies in full.
6. Understand what the project produces or operates and distinguish its
   document-system owners from natural-language artifacts before changing
   registration or topology.

## Working Contract

- Use `mindflow status --json` for complete semantic orientation, begin a
  bounded folder question with `mindflow topology probe DIRECTORY --depth 1
  --max-nodes 128 --mermaid`, and run `mindflow check --json` after semantic
  changes.
- Keep Mindflow Structure, Opening, and Evolve semantics distinct;
  actual files supply names and hierarchy, and `MINDFLOW.yaml` adds only
  registrations, useful annotations, relationships, and SOE records. Mermaid
  is generated output. Use a format `2026-10-20` executable; no legacy compatibility
  carrier is part of this recipe. Procedure remains ordinary guidance.
- Treat profiles as durable design authority and canonical documents as the
  implementation-facing contract. Steering and temporary work never override
  them.
- Let genuinely new or reforming meaning expand in the highest relevant open
  owner. As it stabilizes, absorb its consequences into more exact owners and
  artifacts, then release provisional residue after conservation; let lower
  evidence pressure upstream reform without silently redefining authority.
- Treat an owner as structurally overloaded only when its meanings require
  independent authority or change surfaces; length, density, and mismatch with
  this recipe do not justify a split.
- Keep every durable commitment with one visible owner; link instead of
  duplicating authority.
- Treat document-system membership as a project function, not a consequence of
  Markdown or natural-language form.
- Let managed folder names supply role context. Keep one exact path per stable
  ID and add descriptions only when useful. Register each entry explicitly;
  unregistered ancestors remain context. Names, kinds, and parents come from
  disk and are not authored again.
- Keep ordinary relationships within one actual folder scope; retain exact
  cross-folder claims as prose links when no truthful common layer exists.
  On moves, preserve IDs, update path bindings and links, and revalidate SOE.
- Add structure only for a concrete recurring pressure, and choose the smallest
  folder, owner, or relationship distinction that protects a clear authority boundary.
- Edit ordinary files directly and review Git before completion.
- Preserve existing user changes and distinguish them from current work.
- Absorb or dispose of temporary material; do not archive completed scaffolds.
- Keep the whole region understandable. Do not answer comprehension problems
  with opaque ingestion, retrieval, or hidden context machinery.
